本文描述 DH BOT 与旺商聊之间实际依赖的边界。ZCG 只作为协议行为参考，DH BOT 不启动
`xplugin.exe`、不连接 `51234`、不读取 ZCG 登录链，也不携带下注、账单或结算功能。

## 1. 调用链

```text
DH BOT Rust Gateway
  -> http://127.0.0.1:9222/json/list (选择唯一旺商聊页面)
  -> CDP / Electron xclient IPC
  -> 旺商聊页面的 NIM 方法或 HTTP 业务路由
  -> transport envelope + business envelope
  -> GatewayReceipt
  -> SQLite outbox/action/audit
```

生产端点固定为回环地址。DH 不接受前端传入任意 URL 或任意路由；每种操作由强类型
网关方法构造请求。9222 页面不可访问、页面不是旺商聊、NIM 未初始化和其他程序占用端口
必须分别报告，不能统一显示为“协议不支持”。

## 2. ZCG 基线能力

运行时只读探测会检查路由签名、IPC、NIM 方法和双层响应结构。结构一致时，即使旺商聊
主脚本 SHA 不同，也可以开放对应的 ZCG 基线能力：

| DH 能力 | 基线路由/方法 | 写后验证 |
|---|---|---|
| 群列表 | `/v1/group/get-group-list` | 群 ID 和名称可解析 |
| 成员列表 | `/v1/group/get-group-members` | 名单数量、游标和完整性 |
| 成员详情 | `/v1/group/get-group-member-info` | userId/nimId 和角色 |
| 成员禁言 | `/v1/group/set-member-mute` | 回读禁言截止时间 |
| 成员解禁 | `/v1/group/member-mute-cancel` | 回读为可发言 |
| 修改名片 | `/v1/group/set-member-nickname` 或 NIM 更新方法 | 回读新名片 |
| 移出成员 | `/v1/group/remove-group-member` | 回读完整名单 |
| 撤回消息 | NIM `getHistoryMsgs` + `recallMsg` 优先 | 撤回通知 |
| 全群禁言 | `/v1/group/set-group-mute`，`MUTE_MEMBER` | 回读群发言状态 |
| 解除全禁 | `/v1/group/set-group-mute`，`MUTE_NO` | 回读群发言状态 |
| 发送文本 | `/v1/plugins/encode-msg` + NIM `sendCustomMsg` | 稳定消息 ID/出站回显 |

HTTP 撤回路由返回业务码 `1001`（禁止调用）时是永久失败，不进入退避重试；其他成员
消息必须先使用 NIM 历史消息定位，再调用 NIM 撤回。权限失败不能被误判为协议失效。

## 3. 旺商聊专有能力

群公告不是 ZCG 基线能力。旺商聊公告链使用公告列表、添加/编辑路由（`notice-list`、
`add-notice`、`notice-opt`）和 NIM 广播：

1. 读取当前公告和作者/noticeId。
2. 新公告走 `add-notice`；明确选择旧公告编辑时才走 `notice-opt`。
3. 回读内容和公告消息 ID，确认与提交内容一致。
4. 只有首次手工回读成功后，才开放批量或自动公告。

公告历史由本地群页按公告 ID、时间、作者和来源保存展示；旺商聊更新后若字段结构变化，
只读仍可保留，写入降为 `ManualVerification`。

## 4. 能力状态

```text
Supported          已通过结构探测和必要回读，可按权限执行
ManualVerification 可人工确认，后台自动动作关闭
Unavailable        当前页面/路由/NIM 结构无法使用
Unsupported        当前产品明确不开放
```

每项能力还保存来源（ZCG 契约、旺商聊 Electron、NIM 运行时或人工回执）、原因、检查时间、
协议指纹和自动/人工许可。版本号和脚本 SHA 只用于追踪升级，不单独锁死全部能力。

## 5. 回执结构和错误分类

`GatewayReceipt` 至少包含 request ID、操作、状态、transport code、业务 `code/errno/msg`、
消息/对象 ID、是否需要人工确认和脱敏错误。错误按以下类别归档：

| 类型 | 例子 | 处理 |
|---|---|---|
| Transport | 连接失败、超时、HTTP 5xx | 有界退避；未知副作用不自动重试 |
| NimNotReady | 登录后会话尚未初始化 | 保持等待，重新探测 |
| Permission | 当前账号不是管理员 | 逐项失败并提示权限 |
| NotFound | 群、成员或消息不存在 | 永久失败，记录对象 ID 类型 |
| Business | 双层 envelope 的业务错误 | 按错误码分类；1001 撤回永久失败 |
| Unsupported | 路由或方法不存在 | 降级对应能力 |
| Decode | 字段类型/结构变化 | 保留原始诊断摘要，不保存原响应 |
| Unknown | 请求已发但回执不确定 | 人工确认，不自动补发 |

所有写调用遵守账号级顺序队列，间隔至少 500ms。只读群列表缓存 10 秒、成员名单缓存
30 秒；写后验证绕过缓存。相同刷新请求 single-flight 合并，避免频繁调用旺商聊。

`tauri3/contracts/wangshangliao_capabilities.json` 是按旺商聊版本和脚本指纹归档的人工校准表，

真实采集只在开发版和本机忽略目录进行，仓库只提交确定性脱敏结果：

校验命令和字段要求见 [`tauri3/contracts/README.md`](../tauri3/contracts/README.md)。

目标是独立 Rust 业务客户端和 NIM 传输层，不通过 Node、浏览器或原生模块运行。
当前生产链路仍为 CDP；下面的离线验证不能作为登录、收发消息或群管能力已支持的证据。

### 当前进度（2026-09-16）

本节为最新状态；后续各阶段记录保留当时的结论，不代表当前实现仍停留在该阶段。

- `business_wire` 已还原 mode-1 请求/响应封装，真实官方请求的签名、正文认证、原文哈希、nonce 与元数据绑定均通过独立验证。
- `business_client` 使用 Rust 完成 HTTPS 请求、签名、业务读取和 NIM 令牌续期。登录包含密钥交换、密封响应解密以及时间、请求关联值、账号身份的绑定校验；失败不会安装部分凭据。
- `nim_client` 已实现 Rust LBS 发现、WSS 认证、心跳及显式重连入口。认证响应允许 SDK 省略尾部的端口列表/推送字段；心跳期间的推送保留在有界队列中，踢下线返回明确错误。
- **真实已通过**：已有会话的 Rust 群列表读取 → Rust 续期 → 再次业务读取 → 使用新令牌的 Rust NIM 认证 → 心跳。该结果由 `business_probe` 给出，未发送群消息或执行群管写入。
- **全新登录真实已通过**：2026-09-16 的 `login_probe` 在移除旧 JWT/MAC 后完成 Rust 登录 → 群列表读取 → 续期 → 再次读取 → NIM 发现 → 认证/心跳 → 关闭 → 重连认证/心跳，退出码为 0。没有发送消息或执行群管写入。
- 登录修复点：服务端登录令牌中的 MAC 材料是变长字节字段；原生保存完整材料，SipHash 读取前 16 字节。Rust 现保留最小长度和绑定校验，按原生行为使用前 16 字节，已覆盖 32 字节材料与不足 16 字节的回归测试。
- `dh-server serve-rust` 和 Web 登录表单已接入该客户端。Linux arm64 容器（Rust 1.90/bookworm）通过 27 项协议测试与 3 项服务测试；浏览器真实账号提交尚待单独验收，不能用组件模拟测试替代。

`probe_business_session.py`、`probe_rust_login.mjs` 是研究采样工具，不是生产依赖：固定样本哈希，动态地址基于实际加载基址；配置及人工验证输入仅在内存/子进程标准输入传递，日志只输出阶段状态；断点与页面包装在退出时清理。首次登录探针明确移除旧业务 JWT 和账号 MAC，不能把导入会话当成新登录成功。

目前部署配置及设备签名种子由调用方提供。首次登录的密封交换已独立实现，但尚未提供无官方资源的配置分发/持久化界面；消息同步游标、消息解码与 ACK、生产网关替换、长期离线恢复仍未验收。不要把认证和心跳成功表述为完整群管收发能力。

新增测试覆盖独立 libsodium/xxhash/zstd 业务向量、登录响应与请求/身份不匹配、认证尾部缺省/截断、心跳与推送交错以及踢下线。完整验证命令仍为本页列出的 Cargo test/Clippy。

### 已验证的密码原语

本地样本为旺商聊 2.7.7 的 arm64 `mclient.node`，SHA256：
`a92865e20618267bdeaff72cc2ed355d682e6a5248644a1a213cb47473598851`。
静态地址只适用于此样本，不是 ASLR 后地址，也不是协议字段偏移。

- Node-API 入口：`xinit` 0x329c、`xsync` 0x39f0、`xtask` 0x3d08。
- 解码调用链：0x39f0 → 0x9c4c → 0x21c04；0x2cc88 为 ChaCha 轮函数，0x29650/0x2973c 为 Poly1305 运算。0x2d1b4 是终止路径。
- 已验证解码原语参数为 32 字节密钥、8 字节 nonce、8 字节 AAD 和 16 字节标签。MAC 输入为 `AAD || LE64(8) || ciphertext || LE64(ciphertext_length)`，不采用 IETF 版分段补齐规则；消息流从计数器 1 开始。
- 上层对象 +0x18/+0x20/+0x28/+0x30/+0x38 分别作为 nonce、密文指针、长度、AAD、标签来源。这里只恢复了内存对象布局。
- 密钥参数指向 0x3801c，位于可写数据段；当前直接交叉引用只找到解码调用点，不能据此认定密钥固定或不存在间接写入。
- `xinit` 中 `uname` 后比较 arm64/x86_64 并保存架构标记；这一分支不能作为账号设备绑定的证据。

[`dh-protocol`](../crates/dh-protocol/src/lib.rs) 使用 RustCrypto 原语实现 `MessageCodec::seal/open`。
密钥与成功解密的明文使用 Zeroizing，认证先于解密，标签采用恒定时间比较；失败不返回明文。
`seal` 返回密文拼接标签只是该原语的测试接口，不是已确认的应用网络封装。
调用方必须保证同一密钥下 nonce 不重复；在 nonce 来源还原前不得接入生产发送。

离线测试包含两组不同的合成 key/nonce/AAD，各覆盖长度 0、1、15、16、17、63、64、65、256、1024。
固定向量由 PyNaCl 1.6.2 的 `crypto_aead_chacha20poly1305_encrypt` 独立生成，Rust 双向对照，
并验证逐字节篡改、所有截断长度、错误密钥、错误 nonce 和错误 AAD。
第一组合成参数另用 Unicorn 对原生解码函数执行 10 项成功和 10 项标签篡改验证。

```sh
cargo test --manifest-path crates/dh-protocol/Cargo.toml --locked
cargo clippy --manifest-path crates/dh-protocol/Cargo.toml --locked --all-targets -- -D warnings
# 可选原生对照：本地需 Rizin、Unicorn 2.x、PyNaCl 1.6.x；不分发应用样本。
python tools/verify_native_codec.py /path/to/mclient.node
```

原生对照脚本先校验样本哈希，只仿真指定函数与合成内存，仅模拟清零函数；不运行模块初始化、登录或网络请求。
CI 在 Linux/Windows 上仅执行纯 Rust 格式、测试和 Clippy 门禁，无需桌面依赖。

### 业务与 NIM 的证据及剩余工作

JS 包装层已确认 Protobuf `api.common.Message` 编码后调用 `xtask` 的 encrypt 操作，接收时调用 `xsync`。
登录请求采用单独的 execute 类型；业务会话与 NIM 的 account/token 需要分别追踪，不能将两者视为同一凭据。
NIM SDK 位于打包后的前端资源内，而非独立可直接移植的 Rust 组件。

本轮进一步确认生成的 Protobuf 编码器存在以下字段；仍需对照独立编码向量，尚未接入 Rust：

| 类型 | 字段编号与类型 |
| --- | --- |
| MessageSource | 1 id:int32；2 name:string；3 avatar:string |
| MessageContent | 1 data:string；2 title:string；3 style:int32；4 color:string；5 maskWords:repeated string |
| Message | 1 from；2 to；3 createdAt；4 msgDevice；5 msgSession；6 msgVersion；7 msgSessionId:int64；50 idClient:string；51 idServer:string；99 signature:bytes；100 content |
| TempChat | 1 tempChatId:int64；2 tempChatType:int32 |

Message 表格只列当前核对的字段，不是完整 schema；该消息还有图片、语音、群通知、提及和其他 oneof payload。
不能通过忽略未知字段重新编码整条消息，以免损坏未还原内容。

这验证官方 SDK 连接及同步活动，不证明已解析 NIM 帧或具备 Rust NIM 互操作能力。

- 登录后群列表：transportCode=200、errno=0；响应为 code/msg/data，业务 code=0，data 为对象。
- 调用客户端 app store 自身 refreshToken：无 error，返回非空 nimToken，保存值发生变化，NIM 实例仍存在。
  这是官方客户端续期成功，不证明新令牌重连、过期恢复或纯 Rust 续期成功；未强制断开用户会话。
- 最小合成消息缺少身份和元数据时 encode 返回 403/-236；不能据此判定卡密或许可证限制。
  补齐当前账号身份和消息元数据、仅执行本地编码后返回 code=0/errno=0，response 是含 b 字段的 JSON 字符串。
  未把编码结果发送到 NIM，也未保存包含身份的编码正文。
- 现有 Rust decode_transport_response 已单独允许 encode 路由的 code=0，不需要放宽其他业务路由。
- 新版 encode 先 Protobuf 编码，再将准确 byteOffset/byteLength 对应的 ArrayBuffer 交给 xtask；
  decode 将输入转 UTF-8 Buffer 后切出 ArrayBuffer 交给 xsync。完整网络外壳及 b 字段语义尚未验证。

### Web 通路与协议直连分离

dh-server 是无 Tauri 的 Rust HTTP 宿主，现支持 `serve-cdp` 和 `serve-rust`。
纯 Rust 业务登录、续期及 NIM 认证/心跳已通过探针；Web 共用 82 个业务命令及原有权限和回执处理。
Rust 消息内容编解码、同步/ACK、发送、撤回和新公告通知仍未完成。具体接口范围见 [Rust Web 登录](RUST-WEB-LOGIN.md)。

### 2.8.0 NIM 外层包头解析

响应追踪：2_3 的 SDK schema 依次为 loginRes(Property)、loginPorts(PropertyArray)、
aosPushInfo(Property)。afterLogin 在设置连接 ID 和通知登录后调用 syncData；因此
WebSocket 建立不能代替账号认证，账号认证也不能代替同步完成。
Rust 当前仅提取已解码 loginRes 中 102/103/104 字段并保留原始属性；
尚未实现完整响应解析、状态码与序列号校验，不能用于判断认证成功。

登录构造补证：隔离执行 assembleIMLogin 的两种 loginSDKTypeParamCompat 分支，
确认兼容分支 userAgent=Native/SDK版本、sdkType=0、省略 libEnv；普通分支将
userAgent 截断为 299 个 JS 字符，并从环境函数取得 libEnv/sdkType。
两个合成分支均通过，不使用真实账号或初始化 SDK。
`nim_login::encode` 根据已恢复字段编号生成 2/3 请求，按数字字段排序，拒绝未知和
重复字段，要求基础身份字段非空。该检查不是完整登录前置条件验证；所有环境与
会话值仍由调用者提供，当前未接网络，不能宣称令牌有效或服务端认证通过。

认证载荷静态定位：SDK auth.login 为 service=2、command=3，参数类型为 Property。

业务端点静态定位：2.8.0 资源列出 `/v1/user/login`、`/v1/verify/sms-anon`、
`/v1/user/login_device_change`、`/v1/user/get-change-device-verify`、
`/v1/user/RefreshToken`（资源字符串带前导空格，实际请求封装需校正）。
登录正文由滑块 `validateStr` 与账号/密码或短信 `key`/验证码组成；
这些端点尚未取得真实主机、请求头、签名和响应样本，不能直接在 Rust 中调用。

主进程边界补证：`xclient` IPC 仅允许 `buildIn`、`broadcast`、`request`、`encode`、
`decode`、`decodes` 六类操作；`request` 将 `excuteType`、URL 和参数原样传入
原生 `xtask`。IPC 处理器先调用 `this` 对应方法并等待返回，再调用 `handleCacheStrategy`。
对配置了缓存的 URL，外层 code=200 且响应正文 code=0 时比较数据哈希与请求 tag；
一致则生成正文业务 `code=304`。这是收到原生结果后的本地响应转换，
不能据此推断原生请求被缓存短路。Rust 直连实现必须区分本地回执和服务端结果。

动态分诊（本机、只读）：LLDB 可附加并安全分离 2.8.0 `mclient`；`lsof` 显示其持有
到远端 TLS 的已建立连接及本机 IPC 监听端口。该证据确认原生辅助进程承担网络连接，
但没有读取进程内存、TLS 明文或凭据，也没有定位到稳定的 SSL 调用点。后续必须在
工作副本和授权测试账号上设置受控函数断点/参数脱敏记录，不能从端口号猜测业务协议。

静态 TLS 边界候选（2.8.0 arm64 `mclient`，SHA-256
`815b95a3357b2b22492a5a9fc51dc645e019023459155027a656d1902beb4a70`）：
以 Mach-O 首地址为基准，函数 `+0x83b34` 将入口 x2 保存到 x22，
入口 x3 截至 `0x7fffffff` 后保存到 x24；`+0x83e74` 的 `blr x8`
使用 x1=x22、x2=x24、x3=栈上输出位置。目标来自对象方法表 `+0x48`。

尚未证明缓冲区包含可解码业务明文。`observe_native_socket.py` 新增该位置探针，
验证样本哈希与指令字节后，累计长度及目标代码偏移。为验证所在层次，
在本机内存读取最多 8 个前缀字节，仅输出固定 HTTP 请求/响应/未分类标签；

进一步传输识别：依据 RFC 9113 §4.1/§6（https://www.rfc-editor.org/rfc/rfc9113.html），
增加最多 8192 字节的完整 HTTP/2 候选帧结构检查，仅输出帧类型计数，

HPACK 动态表或解码业务正文，不能据此声称业务封装或 NIM 已还原。
后续先定位头压缩前的名称/值构造及 DATA 封装，避免误把 HTTP/2 压缩头当作业务加密。

头压缩前边界补证：由 `nghttp2_submit_request` 错误字符串交叉引用追踪到
`mclient+0x10801c`。调用点 `+0x2f630` 的 x3 为头数组、x4 为数量；
此前分配和复制循环按 40 字节步长构造元素。内存偏移 0 为名称指针、16 为名称长度，
这些是本样本内存布局，不是网络偏移。哈希及入口指令校验后的有界探针在
2.60 秒只读查询中命中 4 次，每次数组均含 16 项：`:authority`、`:method`、
`:path`、`:scheme`、accept、content-length、content-type，以及 9 个未输出的头名称。
探针不读取头值，仅输出标准名称白名单；查询退出码 0，调试器正常分离。
同窗口 TLS 边界出现 4 组 HEADERS+DATA。下一步可在此入口进行路由及编码的
白名单分类，无需从中途附加的 HPACK 动态表猜测请求头。尚未恢复自定义头的生成规则。

自定义头补证：固定字符串 `X-Token`、`X-Seed`、`X-Hash` 的交叉引用均落在
`+0x1e504` 函数。将样本中的固定名称加入探针白名单后，2.70 秒查询成功且正常分离；
其中两次头数组识别出 x-device、x-hash、x-id、x-jwt、x-request、x-seed、
x-token、x-trace-id、x-version；另两次是不同头集合，不能将其归为同一路由。
所有头值仍未读取。静态数据流显示 `+0x1ef5c` 提交 X-Request，
`+0x1ef80` 从全局对象 +0x48 提交长度 0x20 的 X-Seed 输入；
`+0x1efac` 调用 `+0x27d87c`，输入含 X-Request 的同一指针/长度及全局对象 +8，
随后 `+0x1efc8` 提交长度 0x40 的 X-Hash 输入。
这些长度是本地头构造函数的参数，尚未验证其网络编码。`+0x27d87c` 包含多轮
摘要调用和位裁剪操作，不应仅按 X-Hash 名称实现普通哈希或 HMAC；
需要合成输入的独立算法对照及密钥生成链证据。

算法对照已补齐：`tools/verify_native_signature.py` 在 Unicorn 中按 Mach-O 段布局
加载上述固定哈希样本，仅执行 `+0x27d87c`；不执行初始化、网络或宿主程序。
输入为合成 seed、公钥和消息，外部调用只模拟有界内存操作，其他导入立即失败。
长度 0、1、31、32、63、64、127、128、129、1024 的 10 组输出均与
PyNaCl Ed25519 签名逐字节相同。由此确认该函数为 Ed25519 签名实现，
不是普通哈希/HMAC；此结论不证明真实密钥生命周期、签名输入规范化、
X-Hash 网络编码或服务端验签已打通。测试不读取真实账号或密钥。

头值编码补证：`+0x2032c` 构造名称、冒号和空格后，对非空输入以 flags=7
调用 `+0x26fb8`，再追加到请求头列表；零长度分支跳过编码。
离线 oracle 扩展验证该编码函数：10 个合成签名以及 9 个非空消息输入
均与无填充 Base64URL 逐字节一致（包含 1/2/3 余数及二进制字节）。
空输入直接调用曾达到模拟器指令上限，故不宣称底层编码器支持空输入；
包装函数的跳过行为来自静态分支证据。X-Hash 的 64 字节签名经此路径编码，
但真实 X-Request 字节构造、密钥初始化及服务端验签仍未验证。

X-Request 序列化入口：`+0x1ef30` 调用 `+0x25ecf8`，x0 为对象，
x1 指向静态描述符 `0x1003203b8`，x3/x4 为输出指针和长度位置。
描述符 +8 指向 `0x10028cef4`；序列化器读取描述符 +0x12 的数量（14），
并按 12 字节逆序遍历字段记录。原始表如下；offset 是内存对象偏移，
不是报文字节偏移，末列暂不解释为 Protobuf 类型。

| --- | --- | --- |
| 1 | 0x20 | ff ff 04 c2 |
| 2 | 0x00 | ff ff 05 42 |
| 3 | 0x04 | ff ff 05 42 |
| 4 | 0x08 | ff ff 05 42 |
| 5 | 0x0c | ff ff 05 42 |
| 6 | 0x28 | ff ff 03 c2 |

该表是静态证据，尚无合成对象的序列化回放，不能据表猜造登录请求。
序列化器还读取对象前 8 字节指向的辅助状态；后续模拟必须恢复该状态布局，
不能只分配字段表所示的对象大小。

标量序列化离线验证：oracle 直接调用内部 `+0x25eddc`，提供预分配输出缓冲区，
不模拟未恢复的 arena 分配器。描述符指针在文件中使用 Mach-O chained rebase，
仅将已核对的 `0x1003203c0` 指针解析为 `0x10028cef4`，避免把文件值当运行时地址。
7 个字段分别测试 0、1、127、128、65535、0x7fffffff、0x80000000、0xffffffff，
共 56 组逐字节对照通过：字段 2、3、4、5、7、12 使用 int32 varint（负数
符号扩展至 64 位，编码 10 字节），字段 13 使用 uint32 varint；零值省略。
该结果只验证合成单字段对象，不证明字段业务含义、字符串/字节字段、
完整对象组合顺序、未知字段保留或真实登录报文已恢复。

剩余 7 字段也已完成单字段回放：1、6、8、9、10、11、14 从对象读取
64 位值，以 wire type 0 编码；各 12 组含跨 32 位、最高位和全 1 位模式均通过，
加上先前 56 组共 140 组。全部 14 项均为标量，原先“可能为字符串/字节”的
方向被此证据否定。64 位正负解释不能仅凭 varint 区分，业务语义仍待写入点追踪。
此处确认 X-Request 是标量元数据序列化，不代表业务正文已解码，
也不证明正文如何被纳入认证约束。

构造数据流补证（`+0x1e504`）：字段 2 写常量 1（`+0x1e6b4`）；字段 3
取全局版本整数（`+0x1e6c0`）；字段 7 取请求对象 +0xc8 的低 32 位。
同一 +0xc8 被作为长度、+0xd0 被作为缓冲区传入 `+0x28efc`，返回值写字段 8。
该函数经 19 组独立 XXH3-64 合成边界长度对照（0 至 1024，含 16/128/240 分支）
全部一致。尚未证明此缓冲区是加密前还是加密后的最终业务正文。
字段 10 来自 `+0x251088` 对 gettimeofday 的 tv_sec 拷贝，写入点 `+0x1e6fc`；
因此时间单位为秒而非毫秒（静态数据流）。其余全局/会话字段继续保持未命名，
不能用已验证的哈希与时间字段替代完整请求契约。

正文选取的两条静态路径：`+0x1dfe8` 将回调上下文 +8/+0x10 的长度/指针
复制至请求对象 +0xc8/+0xd0，然后以第三参数 1 进入 `+0x1e504`；
`+0x20534` 则在内部状态 +0x16c 为零时，优先取内部对象 +0x130/+0x138，
长度为零时取 +0x140/+0x148，复制至同一请求位置，以第三参数 0 进入签名构造。
优先缓冲区是否经过加密尚未证实，不能按“处理后”名称赋予加密语义。
`+0x1e02c` 的已读部分包含端点选择、路径拼接和连接参数构造；
尚未建立两个缓冲区的生产者与具体业务路由之间的对应关系。
后续需要分别追踪写入点，不能把某条路径的正文规则套给所有登录及业务请求。

Rust 编码落地：`dh-protocol::request_metadata::encode` 编码 14 个原始整数位模式，
对 32 位字段越界报错，输出采用 Zeroizing 容器。原生离线 oracle 增加 8 组全字段
组合向量，确认字段按编号递增输出；连同单字段向量共 148 组固化于
`crates/dh-protocol/tests/fixtures/request_metadata_280.json`，Rust 逐字节回放通过。
这是新建已知字段对象的编码器，不提供解码/未知字段透传，也不补造缺失业务字段；
不得因该模块可用就启用尚未恢复的登录请求。

签名密钥初始化补证：`+0x1369c` 中，存储读取结果非空且长度为 0x48 时，
将 72 字节复制到全局密钥对象；否则写入当前秒数并调用 `+0x27d774` 生成密钥，
